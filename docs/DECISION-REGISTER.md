## DEC-029 supersession record

Classification: REPLACEMENT. Supersedes DEC-005.

| Field | Value |
|---|---|
| Previous behavior | DEC-005 locked the agent set to exactly four CLIs: Claude Code CLI, Hermes Agent CLI, Kilo Code CLI, Cline. Each had an `agent_type` wire identity, an adapter-capability record and a native transport contract. |
| New behavior | The agent set is exactly three CLIs: Hermes Agent CLI (`HERMES_AGENT`), Kilo Code CLI (`KILO_CODE`), OpenCode CLI (`OPEN_CODE`). `CLAUDE_CODE` and `CLINE` are removed from every machine-readable registry. Hermes and Kilo are unchanged. |
| Reason | Product decision to restrict Mayasaba's coordination surface to the three retained CLIs. OpenCode CLI is admitted as a new agent; Claude Code CLI and Cline are withdrawn from the product. |
| Compatibility impact | Breaking wire-contract change. `agent_type` is a closed enum in exactly six schemas — `agent-adapter-v1/adapter-types`, `agent-adapter-v1/native-event`, `agent-adapter-v1/probe-result`, `doctor-v1/doctor-report`, `mcf-v2/handshake` and `mcf-v2/identity` — so any retained handshake, native event, probe result or doctor report carrying `CLAUDE_CODE` or `CLINE` becomes invalid. (`mcf-v2/identity` also admits `null`, because it is a shared envelope actor descriptor in which a `MAYASABA` actor has no agent type.) Native transport identifiers `CLAUDE_STREAM_JSON` and `CLINE_JSON` are removed. |
| Migration/reconciliation | No data migration is required. `agents.agent_type` in `schemas/sqlite-v1/schema.sql` is `TEXT NOT NULL` with no CHECK constraint, so SQLite does not constrain the value, and no Mayasaba database has been created yet. There are no installed adapters and no persisted sessions to reconcile. Reject-with-diagnosis is the only runtime path for a legacy `CLAUDE_CODE` or `CLINE` value. |
| Tests affected | Contract verification (`tools/contracts/verify.mjs`) must pass. MCF-v2 fixtures that assert agent identity must use a retained `agent_type`. Adapter conformance fixtures are required for `HERMES_AGENT`, `KILO_CODE` and `OPEN_CODE` before any adapter is admitted. |

Scope note: this decision governs the agent set Mayasaba coordinates at runtime. It does not change which coding agents may contribute to this repository. `AGENTS.md` §1 applicability and the contributor rules in `AGENTS.md` are unchanged by DEC-029.

## DEC-029 verification annex

Classification: ADDITIVE. Date: 2026-10-03. This annex records the evidence that admitted the three-CLI set and hardened its adapter contract. It adds no new decision and does not alter the supersession record above.

The set was admitted against three checks, run before the adapter contract was hardened.

| Check | Result |
|---|---|
| Headless mode exists and is scriptable | Pass for all three. Each accepts a prompt non-interactively and emits a structured stream: `hermes chat -q <prompt> --format stream-json`, `kilo run <prompt> --format json`, `opencode run <prompt> --format json`. Hermes was verified first-hand by running a task headlessly and capturing the raw JSONL. |
| Event streams normalize to the adapter schemas | Pass with schema changes. Kilo and OpenCode emit event kinds the `native_kind` enum did not yet cover — `REASONING`, `STEP_START` and `STEP_FINISH`. Hermes's stream-json records (`system/init`, `text`, `tool_use`, `tool_result`, terminal `result`) all map onto kinds the enum already had, so Hermes forced no schema change. The enum was extended from 12 to 15 values, exactly matching the three additions. |
| Actively maintained | Pass for all three. All three show current commit activity and release cadence. |

Findings that changed the contract, each recorded in `schemas/agent-adapter-v1/native-transport-contract.json`:

| Finding | Consequence |
|---|---|
| Kilo Code CLI is a fork of OpenCode CLI. | Corroborated three ways: 747 `opencode` strings in the Kilo binary including `@opencode/LLMClient` and `@opencode/FileSystem`; `kilocode_change` markers in `bin/kilo`; and vendor documentation stating "The Kilo CLI is a fork of OpenCode and supports the same configuration options." Kilo and OpenCode therefore do not provide independent corroboration in council deliberation; model/provider diversity is unaffected. This weakens the CLI-independence argument for the three-CLI set but not the set itself. |
| Kilo ingests `~/.claude/*` by default. | The adapter must set the seven `KILO_DISABLE_*` variables. `OPENCODE_DISABLE_CLAUDE_CODE` has no effect on the Kilo binary. |
| Kilo indexes the codebase by default and uploads embeddings to a configured vector store — an egress path independent of session sharing. | `KILO_DISABLE_CODEBASE_INDEXING=1` became a required variable. Disabling share does not close this path. |
| OpenCode 2.x has no workspace flag, and its `run` path resolves the root from `PWD` without changing directory. | A version gate was added: `1.x` admitted, `2.x` unverified. The adapter branches on the probed version and fails closed on an unclassifiable one. On 2.x it must supply the workspace as the child working directory **and** set or clear `PWD`, because an inherited stale `PWD` would otherwise point the agent outside the authorized workspace. Verified against the `v2.0.22` tag; the earlier wording ("2.x rejects `--dir`") was replaced as unsupported. |
| Hermes defaults `updates.check` to true and reaches the network on startup. | `updates.check: false` became a required launch precondition. No launch flag disables it and `--safe-mode` is a trap: it implies `--ignore-user-config`, blanks the model and exits 1. |
| Hermes ACP cannot suppress context injection. | ACP was dropped for Hermes; `stream-json` is its sole transport. |
| Session upload has three independent triggers in OpenCode and Kilo (config `share: "auto"`, the `*_AUTO_SHARE` env var, and the `--share` flag), not one. | Blocking the flag alone was insufficient. Both agents now require `share: "disabled"` in config — a string enum, not a boolean — plus the env var, and Kilo additionally requires its own hard kill switch `KILO_DISABLE_SHARE=1`. |
| Kilo's `--auto` is retained in the launch vector, and the permission precondition that makes it safe is enforceable. **Ruling (user-delegated):** keep `--auto`; do not strip it. | The stated basis for stripping it — that the precondition "depends on a probe capability that doesn't exist yet, so it is currently unenforceable" — is superseded by evidence. `KILO_CONFIG_CONTENT` is a documented Kilo config channel (embedded reference: "Inline JSON config string (high precedence, after project dirs)"), it resolves at origin `local`, and it demonstrably outranks the user's global config (injected keys show `permission_origins` `local`, user-config keys `global`). The verification surfaces exist and are machine-readable: `kilo debug config` emits the resolved config plus `permission_origins`, and `kilo debug agent <name>` emits that agent's resolved permission array. Verified against kilo 7.8.1. |
| The permission map the adapter injects must be **default-deny with an explicit allow-list**, not a list of specific denies. | The earlier four-deny form (`bash`, `external_directory`, `webfetch`, `websearch`) is insufficient. Several privileged tools are governed by **no named permission key** — only the wildcard `*`: `cron_create`, `schedule_wakeup`, `task`, `board_post`, `link_pr` and `todowrite` resolve to `allow` under the global config and are not closed by denying the four keys. Measured: the four-deny list leaves 25 tools enabled; the default-deny allow-list leaves exactly six (`read`, `glob`, `grep`, `edit`, `write`, `semantic_search`). Note the converse — a tool that *does* name a key is correctly blocked by a targeted deny, so `background_process` (which asks under `bash`/`external_directory`) is stopped by `bash: "deny"`; a hypothesis that it escaped the four-deny list was tested end-to-end and refuted. Kilo's own built-in restricted profile uses the same `{"*": "deny"}` base, so the shape is the vendor's. Recorded in the contract as `required_config_injection`. |
| `--auto` auto-approves anything that resolves to `ask`, so a residual `ask` is an approval rather than a prompt. | The headless permission loop reads `if(auto){reply:"once"}else{... reply:"reject"}`: with `--auto` an `ask` is approved, without it the same `ask` auto-rejects. A deny is terminal in `Permission.ask` and never reaches that loop. This is why the default-deny base is load-bearing — it converts residual `ask` entries (`bash`, `external_directory`, `read *.env`, `doom_loop`, the memory keys) into `deny`. Within a pattern map the last matching pattern wins (`findLast`), so the nested `read` map must list `"*": "allow"` before `"*.env": "deny"`; reversing it would silently re-open Kilo's own secret-file read guard. |
| The permission probe path must not itself execute. | `kilo debug agent <name>` reports configuration, but the same command with `--tool <id> --params <json>` EXECUTES the named tool. An adapter author who used `--tool` to "test" whether an operation is permitted would perform unmediated execution during admission. The contract now states the probe MUST use `kilo debug config` and `kilo debug agent <name>` WITHOUT `--tool`. |
| Kilo's forbidden-command and forbidden-flag lists were incomplete for a network/install surface the admitted binary exposes. | An adversarial audit of the installed binary (kilo 7.8.1) found reachable paths the list did not name: `plugin`/`plug` (installs an arbitrary npm module into config), `upgrade`/`uninstall` (network install and removal — `KILO_DISABLE_AUTOUPDATE=1` closes only the automatic path), `mcp add --url`/`mcp auth` (remote MCP server), `console` (local service, same class as the already-forbidden serve/daemon), `roll-call`/`profile` (network calls), and the GLOBAL `--mdns`/`--mdns-domain` flags, which are reachable on the ADMITTED `acp` vector and default the hostname to `0.0.0.0`. All were added; the admitted acp invocation must bind `127.0.0.1`. |
| Hermes's approval bypass has four spellings, not two. | Blocking `--yolo` and `--accept-hooks` was insufficient: `--accept-hooks` documents itself as "Equivalent to `HERMES_ACCEPT_HOOKS=1` or `hooks_auto_accept: true`", and `--yolo` sets `HERMES_YOLO_MODE`. A child inheriting either variable, or a user config with `approvals.mode: off`, reaches the same bypass. The adapter must also scrub both variables and neutralize a config that disables approvals. |
| OpenCode 2.x's run path DOES chdir, contrary to the contract's earlier wording. | The field said the run path "never chdirs", read from the thin handler `packages/cli/src/commands/handlers/run.ts`. ## DEC-034 canonical event hash chain record

Classification: ADDITIVE. Date: 2026-10-03. Adds one decision; supersedes none. HARD_LOCK.

| Field | Value |
|---|---|
| Affected subsystem | Persistence (SQLite storage owner); consumed by traceability, evidence and recovery. |
| Previous behavior | Events were append-oriented and immutable by convention. No mechanism existed to detect a rewritten, deleted or reordered event: the immutability rule was asserted in prose and enforced only by the discipline of the writer. `events` carried no chain fields, so a database whose history had been altered was indistinguishable from an intact one. |
| New behavior | Every row in `events` carries `prev_hash` and `event_hash` forming a per-project SHA-256 hash chain. `event_hash` is SHA-256 over the RFC 8785 JCS serialization of `{prev_hash, event_id, project_id, session_id, event_type, sequence, correlation_id, causation_id, epoch, payload_json, created_at}`; the first event of a project chain uses a genesis `prev_hash` of 64 zero characters; events with a null `project_id` chain by `session_id`. | Reason | The immutability rule is load-bearing for traceability, evidence and certification, all of which claim that history cannot be silently rewritten — but a rule that cannot be verified is only a convention. The chain makes the existing property checkable without introducing a second hashing convention: it reuses the DEC-025 canonicalization rule already used by the context state digest. |
| Compatibility impact | ADDITIVE. Two NOT NULL columns and one index are added to `events`; no MCF envelope, message, event, transition or Tauri contract changes, so contract verification is unaffected. The event *count* is unchanged. |
| Migration/reconciliation | No data migration is required: no Mayasaba database has been created yet and there are no persisted events to backfill. Applying the columns is a schema change recorded here as a required implementation implication. |
| Tests affected | Chain fixtures recorded in `MEMORY-CONTEXT.md`: a valid chain verifies; a mutated field breaks verification at that event and every later event; a deleted event breaks the chain at its successor; a reordered pair breaks the chain; two projects chain independently; events with a null project_id chain by session. |
| Known limitation | A plain hash chain detects accidental corruption, partial edits, deletion and reordering. It does not detect a deliberate rewrite that recomputes every subsequent hash, because no key is involved. Keyed authentication would require a managed secret, which the security rules place outside ordinary configuration; that trade was declined for a single-user local application and is recorded here explicitly rather than left implied. |

### DEC-034 implementation status, stated plainly

DEC-034 declared the chain on 2026-10-03 and it was **not implemented**. `create_project` wrote
`prev_hash = "genesis"` and `event_hash = "genesis:<event_id>"` — a deterministic placeholder that its own
comment described as a placeholder, and whose genesis value contradicted the 64-zero value this record
specifies. No SHA-256 existed anywhere in the workspace, and `SQLITE-DATA-ARCHITECTURE.md`'s required invariant
"event_hash equals the recomputed chain hash" was checked by nothing. The defect was found while starting M2:
`MCF-V2-IMPLEMENTATION-DESIGN.md` requires a domain transaction to write its state mutation, its immutable event
and its outbound record atomically, so the bus cannot append a correctly chained event while the chain does not
exist.

Implemented 2026-10-05 as the prerequisite for M2, and added to M2's "SQLite event log" item. What exists now:
`crates/storage/src/canonical.rs` implements the RFC 8785 JCS subset the declared field set contains and the
SHA-256 over it; `crates/storage/src/chain.rs` implements the chain rule and its verification;
`Storage::append_event` is the only way a chain link is written, so `prev_hash` and `event_hash` cannot be
supplied by a caller; `create_project` routes its genesis event through that same writer; and `Storage::recover`
reports a break as `EVENT_CHAIN_BROKEN`, because "has durable history been altered?" is a recovery question.

Three points this record left open, and the reading taken:

- **`payload_json` is hashed as a JSON string containing the stored text**, not re-parsed and re-serialized. The
  stored text is the authoritative value, and re-serializing would make an intact row's hash depend on a JSON
  writer's key order and number formatting, so two readers could disagree about a row neither had altered.
- **A chain is ordered by `sequence`, with `rowid` breaking ties.** `SQLITE-DATA-ARCHITECTURE.md` and
  `MEMORY-CONTEXT.md` both say "ordered by `sequence`", and `events` declares neither uniqueness nor `NOT NULL`
  on that column, so ties are possible and a row may carry none. A row with no `sequence` has no declared
  position in an ordered chain, so verification reports it (`EVENT_UNSEQUENCED`) rather than placing it. Because
  the order is derived rather than stored, physically reordering rows is not corruption at all; the detectable
  form of "reordering" is a changed `sequence`.
- **Each link is compared against the recomputed hash of its predecessor**, not the predecessor's stored
  `event_hash`. This is what makes corruption cascade, and therefore what makes this record's own claim — that a
  mutation breaks "that event and every later event" — true rather than approximately true.

Reconciliation for an existing database: none is required, because DEC-034 records that no Mayasaba database has
been created. A database created before this change would now report its genesis link as `EVENT_CHAIN_BROKEN`
rather than being silently accepted, which is the intended behaviour for a link that does not satisfy the rule.

### DEC-043 entity storage resolution

Design note: an entity may satisfy the check by table, by declared column, or by declared alias. That is deliberate. It means "this entity is derived" is a recordable decision with a stated reason rather than a silent omission, which is the distinction the check exists to preserve.

### DEC-044 brief versioning is not epoch advancement

`MEMORY-CONTEXT.md` establishes that the intake router's classification is advisory and that the owning service decides whether a contribution is material, with the epoch advancing only on an actual material truth change. It did not say whether a `ProjectBrief` version bump is itself material.

It is not. A brief version records that the statement of intent was restated or refined; whether project truth changed is a separate judgement made by the owning service.

- Editorial or clarifying restatement producing a new brief version: **no** epoch increment.
- A new material constraint producing a new brief version: epoch increments, once, by the owning service.

The two counters are therefore independent. An implementation MUST NOT derive `epoch++` from `version++`; that would make every rewording of a brief an invalidation of every agent's context.

### DEC-045 the analysis anchor is established by one transaction

DEC-030 makes the brief version current when DISCOVERY closes the immutable analysis anchor for that lineage. "Close" needed a deterministic owner, and the anchor must be read and fixed inside the transaction that performs the transition.

Only the transaction advancing `DISCOVERY → INDEPENDENT_ANALYSIS` may write the analysis anchor, and it writes the brief version current **as of that transaction**. No other transition may set or change it, and no consumer may resolve it as "whatever brief is current now."

Without this, two agents entering the first independent round could observe different brief versions at the boundary, and the anchor would be a lookup rather than a fact. DEC-030's protection against rewritten history depends on the anchor being immutable once written, which requires exactly one writer.

### DEC-046 per-lineage delivery tuple

`AGENT-INTEGRATION.md` requires that every agent receive the same analysis-anchor brief. The stronger and correct form of that requirement is a tuple, not a body of text: for one analysis lineage, every agent must receive the same `(brief version id, project epoch, context snapshot id, state digest)`.

Delivering identical text is insufficient, because two agents can hold the same brief body while differing in the derived state it was interpreted against. The tuple is what must match. The context machinery already carries all four values, so this is a statement of the invariant the existing fields jointly express, not a new mechanism.

### DEC-051 `operation_id` is conditional, and the envelope validator's contract surface is generated

Classification: REFINEMENT. The MCF-v2 envelope contract is corrected; no message type, event, state machine,
Tauri surface or SQLite shape changes.

Found by auditing the Stage 5 envelope validator against `envelope.schema.json`. That module stated that "the
validator and the contract cannot disagree about what is legal". Ten disagreements were reproducible against the
built crate, in both directions. They are one defect class rather than ten: wherever the validator hand-copied a

| Field | Value |
|---|---|
| Previous behavior | `envelope.schema.json` listed `authorization_context` **twice** in its conditional `required` (seven entries, six unique), which is not a conformant JSON Schema: the elements of `required` must be unique. | New behavior | The duplicate is removed. `operation_id` is a **conditional** field: required and non-null of material-action messages, optional otherwise. The conditional narrows all six of its fields to non-nullable types, so the contract itself states what Rust was enforcing alone. Every nested field set — `authorization_context`, `security`, and the identity shape shared by `sender` and each recipient — and every field's JSON type is generated into `generated/envelope.rs` from the contract. The validator enforces `additionalProperties:false` at every level, plus `enum`, `const`, `uniqueItems`, `minLength`, `minimum` and `pattern`. |
| Reason | This record introduces no new product choice. It aligns the machine-readable schema with what DEC-027 and `MCF-V2-PROTOCOL.md` already state: `operation_id` is a conditional field, and material-action idempotency is keyed by `project_id + operation_id`. DEC-027 is unchanged. A schema that demands a field the protocol document classifies as conditional makes a legal non-material envelope illegal at the runtime boundary for no stated reason; the reverse direction — a validator accepting what the contract refuses — lets an envelope reach the bus without the `required_capabilities` PolicyService consumes, and lets a sender smuggle an unvalidated key past a nested `additionalProperties:false`. |

## DEC-052 council decision-quality record

Classification: REFINEMENT of DEC-033 plus ADDITIVE. Date: 2026-10-04. Supersedes none. HARD_LOCK.

The council had a sound deliberation *process* and nothing that ensured or measured the *quality* of what it
decided. DEC-033 bounded deliberation in time (rounds) and gave termination a vocabulary. It did not make
depth proportional to risk, did not grade the evidence a convergence rests on, did not distinguish independent
agreement from two forks of one codebase agreeing, gave the chair's `SYNTHESIS` no independent check, and left
no record of whether a decision later held up. This record closes those gaps without adding a state, an edge,
a message type or an event.

| Field | Value |
|---|---|
| Previous behavior | Every material decision received the same deliberation depth: a full round or nothing. `outcome_type` was the only quality-relevant record. `COUNCIL-ENGINE.md` required an unsupported claim to be *labelled* an assumption, but nothing computed, stored or enforced a grade, so a round could seal `CONVERGED` on opinion. Corroboration was implicitly per-agent, which counts Kilo and OpenCode — one codebase served by two front ends — as two independent witnesses. `SYNTHESIS` was required to cite every contributing position and to come from the chair, and was then self-certified: no non-chair review existed. Only rounds were bounded; there was no wall-clock, token or spike budget, and `repair-policies.json` — the precedent DEC-033 cited — has no machine-readable consumption rule and no implementation at all. | New behavior | (1) **Modes.** `SOLO`, `REVIEW` and `FULL` are selected **deterministically by the controller** from structured inputs: decision class, blast radius, prior validation-failure and dispute counts, and an explicit user override. No LLM chooses, and no agent may select or downgrade a mode. A `ModeSelection` record is persisted for **every** material decision point, including `SOLO`, carrying the mode, the inputs, the reason list, the selector version and the override source; `SOLO` creates a record and **no round**. Exhaustion produces an existing outcome and never silent acceptance. Where an adapter does not report token usage, time and round budgets are enforced and tokens are recorded as `UNAVAILABLE` — never invented. Paused time is excluded from wall-clock and recorded. (8) **Outcome tracking.** Append-only tables record whether a decision later held, was amended, reversed or stayed unresolved, derived **only** from controller facts (validation results, the `reopen_decision` command, decision supersession), with `HELD` requiring a validation evidence reference. (9) **Failure handling.** An offline agent or a provider drop pauses the round through the **existing** `barrier` machine, records non-participation, and surfaces which agents are offline; silence is never agreement and a timeout is never assent. |

### Error codes emitted but not registered, reported and not fixed

`schemas/error-v1/registry.json` is the canonical error-code vocabulary every subsystem's explicit error codes
are drawn from. Eleven codes are emitted by the slice and are **absent** from it: the five
`WorkspaceRejection` codes `WORKSPACE_EMPTY`, `WORKSPACE_DOES_NOT_EXIST`, `WORKSPACE_NOT_A_DIRECTORY`,

workspace branch), and `EMPTY_FIELD`, `BLANK_INITIAL_BRIEF`, `INTAKE_NOT_IMPLEMENTED`, `STORAGE_FAILURE`,
`SERVICE_POISONED`, `TRANSPORT_FAILURE`. The registry contains exactly one `WORKSPACE_*` code,
`WORKSPACE_MISMATCH`, which no implementation emits.

mechanical one: a registered code needs a `mcf_code` and a `tauri_code` and a stated meaning, and inventing ten
of those to satisfy a gate would be inventing a contract to match code — the direction AGENTS.md §5 forbids.

verification result while creating ten contract entries nobody has reviewed. The correct fix is a decision
about the vocabulary plus a gate check that reads emitted codes, and that is named here as remaining work.

**Resolved by DEC-055.** All eleven codes are registered, with a stated meaning each; `mcf_code` is `null` for
them, because none crosses the MCF protocol and the protocol's code enum is closed; and the gate now reads the
codes the implementation produces and fails on any the registry does not declare, so the second reason above no
longer holds. The count in this section is eleven and the figure in this record's "Known limitations" row said
five; the row has been corrected to eleven, which is the count its own body states and the count the gate
measures. DEC-055 also deletes the `create_project` arm that gave `EMPTY_FIELD` a second meaning.

## DEC-058 durable local communication bus record

Classification: **ADDITIVE** at the bus's public surface, at one index and at one registry code; **REFINEMENT** at the genesis payload's encoding and at two registry meanings; one **defect fix** in `create_project`.

| Field | Value |
| --- | --- |
| Decision | The durable local communication bus is the boundary every MCF-v2 message crosses, and it owns the `message_delivery` machine that `schemas/mcf-v2/transition-types.json` assigns to `owner: crates/bus`. Its first operation, `enqueue`, takes envelope **text**, validates it with the protocol crate's own validator, and then writes the message, its queue entry and both of the machine's first two transitions in one transaction. Every value the bus derives is derived from something already durable rather than from a caller's convenience, every state it writes is a state the machine declares, and every refusal names a registered registry code. |
| Previous behavior | `crates/bus` was a two-line stub: no enqueue, no dispatch, no inbox, no error vocabulary, no tests. Four facts made the outbound path impossible to build as declared. (1) **The envelope was not readable.** `crates/protocol`'s `Envelope` exposed two accessors, `message_type()` and `project_id()`, so any consumer of the other nineteen fields had to reach into `Envelope::value`, a public `serde_json::Value`. The bus cannot take that route: `workspace.manifest.json` declares `crates.bus.depends = ["protocol", "storage"]` and the gate enforces the dependency set, so a JSON library is not available to it. (2) **The genesis payload was not JSON.** `create_project` assembled `payload_json` with `format!`, interpolating `local_path` between quotes; a Windows path is full of backslashes, and `\U` is not a legal JSON escape, so **every** project created from a real Windows path stored a payload no JSON parser accepts. (3) **The idempotency scope had no index.** `operation_id` is an optional envelope field with no column, so the canonical `project_id + operation_id` scope (DEC-027, and the implementation design's "Idempotency scope") is only reachable through `json_extract(envelope_json, ...)`, and no index covered it. (4) **A protocol error code was unreachable.** `MCF_DUPLICATE_CONFLICT` was one of the 25 members of `schemas/mcf-v2/error.schema.json`'s closed `code` enum with no registry code mapping to it, because no registered condition had yet needed it - and the enqueue path is the first condition that does. |
| New behavior | (1) **The envelope gate is the protocol crate's validator, not a second opinion.** `Bus::enqueue(&str)` calls `parse_envelope`, which parses *and* validates. (2) **Typed accessors, following the existing convention.** `crates/protocol`'s `Envelope` gains a reader per field the bus needs. A field the contract *requires* reads infallibly (`&str`, `i64`, `bool`, empty or zero if absent); a field it makes *optional* reads as an `Option`. `sequence` and `project_epoch` are the contract's only two integers and it requires both, so both read infallibly and there is no optional-integer reader. `to_json_text()` returns compact, key-sorted JSON and `payload_json_text()` returns the `payload` member alone. (3) **One transaction, four writes, two declared transitions.** `enqueue_message` inserts the `messages` row at `delivery_state = 'PERSISTED'`, inserts the `outbox` row at `dispatch_state = 'PENDING'` with `next_attempt_at = created_at` and `attempts = 0`, appends a `MESSAGE_PERSISTED` event, updates the message to `'QUEUED'`, and appends a `MESSAGE_QUEUED` event - all in one transaction. **Two events, not one**, because the machine declares two transitions and each has its own canonical event; collapsing them would silently drop a declared transition. They are ordered by the chain but not separately observable, because they commit together. `next_attempt_at = created_at` so "is this due?" is one comparison for a first attempt and a retry alike. (4) **The event position is derived, not supplied.** `NewEvent` no longer has a `sequence` field; `append_event_in` computes `MAX(sequence) + 1` within the event's chain scope. A caller that could name its own position could name one that is already taken, which would leave the chain's order ambiguous. This is a different quantity from `messages.sequence`, which is the envelope's declared per-`(session_id, channel)` position and stays caller-supplied. (5) **`outbox.dispatch_state` is declared.** The canonical schema puts no `CHECK` on it and no document declared its vocabulary, so this record declares it: `PENDING`, `DISPATCHED`, `FAILED`, `ABANDONED`. Only `PENDING` is reachable today. (6) **The ids are derived from the message id.** `outbox_id` is `obx_{message_id}` and the two lifecycle event ids are `evt_{message_id}_{event_type_lowercased}`, because `outbox.message_id` is `UNIQUE` and the relation is one-to-one, so deriving makes the identity checkable by reading the id. This is a deliberate choice against an injected id source; replay will need one, because it mints a genuinely new `message_id`, and that is a later slice. (7) **The idempotency scope, and the rule that tells a retry from a conflict.** Dedupe is tried in a fixed order: the same `message_id` already enqueued, then the same `(project_id, operation_id)`, then an occupied `(session_id, channel, sequence)`. The first two are absorbed and return the stored message, which is what every `message_delivery` record's own `idempotency_behavior` requires: "duplicate transition request returns the existing transition/outcome without repeating side effects". A retry that reuses the operation with a **different body** is refused as `IDEMPOTENCY_CONFLICT`, and the body compared is the envelope's `payload`, not the whole envelope - a retry legitimately carries a new `message_id`, `sequence` and `created_at`, so whole-envelope comparison would call every retry a conflict. Storage extracts the stored payload with `json_extract` so the comparison is between two normalized documents, and the bus stores the **canonical re-encoding** of the envelope rather than the caller's bytes so that two spellings of one message compare equal. (8) **A new registry code, and two widened meanings.** `DUPLICATE_CONFLICT` is registered (`category: SEQUENCE`, `retryability: NEVER`, `severity: ERROR`, `mcf_code: MCF_DUPLICATE_CONFLICT`), which gives that previously unreachable protocol member its first registry code; it is deliberately not `SEQUENCE_GAP`, because nothing is missing - two distinct messages claim one place. `PROJECT_MISMATCH`'s meaning is widened from the inbound direction only to cover a message naming a project that does not exist, and `IDEMPOTENCY_CONFLICT`'s from "an idempotency key" to the canonical `project_id + operation_id` scope, because in both cases the registered meaning was narrower than the condition the code now describes and leaving it would put documentation and implementation in disagreement (AGENTS.md §19). (9) **One additive index, and the precondition it exposes.** `idx_messages_operation ON messages(project_id, json_extract(envelope_json, '$.operation_id'))` covers the idempotency lookup. An index is safe to add to a database that already exists because `open()` re-executes the whole schema batch and `CREATE INDEX IF NOT EXISTS` is a no-op when present; a new column would not be, because there is no migration runner. The index also makes an existing precondition explicit: `json_extract` raises on malformed input, so `envelope_json` **must** be JSON for the declared idempotency scope to work at all - and without a check the same malformed text would be refused when the message carried an `operation_id` and accepted when it did not. Storage therefore refuses it once, by name, as `MalformedJson`, using SQLite's own `json_valid`. (10) **The genesis payload defect is fixed.** `create_project` builds its payload with the canonical writer, so a Windows path is escaped and the document is JSON - which matters twice over now, because DEC-034 hashes that text into the chain. (11) **The gate scans the bus's error mapping.** `crates/bus/src/error.rs` is added to the gate's declared `mappingSites`, so a code the bus names that the registry does not register is a failure, and per DEC-057 that new check carries its own mutation proofs. |
| Reason | The bus is where a message stops being text and becomes durable, so it is the one place where "was this already delivered?" and "is this the same request?" have to be answered against stored state rather than in memory. ### DEC-058 dispatch, retry, backoff and dead letters

| Field | Value |
| --- | --- |
| Decision | The bus dispatches from its durable queue, decides each entry's fate from **stored** state, and terminates an exhausted message through the machine's own declared edge. A handover goes to a `Transport` the caller supplies; a refused handover is recorded as an attempt and a backoff, never as a state change; and an exhausted budget ends the message at `EXPIRED` with a dead letter. The retry and dispatch numbers are configuration in `schemas/mcf-v2/bus-policies.json`, shipped as the crate's defaults and cross-checked against them by the gate. |
| Classification | **ADDITIVE** at the crate's surface (four new modules, two new `Bus` operations), at one new canonical artifact and at three indexes; **REFINEMENT** at one stored value's spelling; no change to any machine, state, edge, transition, event, command, table or column. |
| Previous behavior | After the enqueue slice the bus could persist a message and queue it, and nothing could take it out of the queue. `outbox.dispatch_state` was written `PENDING` and never changed; `message_attempts`, `message_receipts`, `inbox` and `dead_letters` were empty by construction; `outbox.next_attempt_at` was copied verbatim from the envelope's `created_at`; and the bus had no clock, no transport and no policy. Three consequences were latent rather than visible. (1) **The policy had no owner.** The retry count and backoff shape existed only as a sentence in `docs/MCF-V2-IMPLEMENTATION-DESIGN.md` ("Backoff is bounded and deterministic from stored retry policy/attempt state"), with no file declaring them and no check tying any implementation to them. (2) **A failed handover had no vocabulary.** The registry registers `ADAPTER_UNAVAILABLE`, `TIMEOUT` and `ADAPTER_PROTOCOL_ERROR` for exactly this, and nothing had ever produced them; `TRANSPORT_FAILURE`, which reads like the obvious candidate, is the frontend side of the Tauri boundary with `mcf_code: null`, so it was available and wrong. (3) **`next_attempt_at` was not comparable.** `created_at` is typed `format: date-time`, which admits an offset, and the column was filled with whatever spelling the sender used - so any future "is it due?" comparison would have been a comparison between two spellings of time. |
| New behavior | (1) **A pure decision.** `dispatch::decide(attempts, policy)` returns `Send { attempt_no }` or `Expire { attempts }` and does nothing else: no clock, no database, no transport. The attempt count it reads comes from `outbox.attempts`, so the budget survives a restart - a dispatcher that counted in memory would retry forever a message that crashed the process on every attempt. (2) **One pass.** `Bus::dispatch_due(clock, transport)` claims the due entries, decides each one, and acts: on success it records the attempt and advances `QUEUED -> DISPATCHED` (event `MESSAGE_DISPATCHED`, command `ADVANCE_MESSAGE_DELIVERY`); on refusal it records the attempt and schedules the next one; on exhaustion it terminates through `QUEUED -> EXPIRED` (event `MESSAGE_EXPIRED`, command `EXPIRE_MESSAGE`) and writes a `dead_letters` row. It returns a report of what it did rather than logging, because this crate performs no I/O. (3) **A refused handover does not move the message.** This is the constraint accepted for this work: the machine declares no transition for a failed transport attempt, so the message stays `QUEUED` and the failure lives in `message_attempts`. `DISPATCHED` therefore means "handed to the transport" and never "the transport was tried". Because a failed attempt is not a transition, it appends **no event** - the event log records transitions, and inventing an event for a non-transition would put a name in the log that no contract declares. (4) **Exhaustion expires rather than dead-letters.** The terminal state is `EXPIRED`, and `DEAD_LETTER` stays reserved for the declared `PROCESSING -> REJECTED -> DEAD_LETTER` path, which is a receiver refusing a message it received. A sender that never managed to hand one over has not been refused. (5) **The outbox vocabulary gains its second and third values, and they mean different things.** `PENDING` is "not yet attempted" and `FAILED` is "the last attempt failed and a retry is scheduled"; both are claimable, and `DISPATCHED` and `ABANDONED` are terminal. Making `FAILED` unclaimable was the first implementation, and the tests caught it: a failed entry could never be retried, so a transient outage would have stranded every message in the queue. (6) **The backoff is anchored at the attempt, not at the previous due time.** The delay is `base_seconds * multiplier^(attempt_no - 1)`, capped, computed from the recorded count and the policy alone - no jitter, no sampling - and added to **the instant the attempt finished** by SQLite. Anchoring at the previous due time would schedule the retry in the past whenever a pass ran late, and a late pass is exactly what happens after downtime. (7) **The clock is injected and the bus ships no formatter.** `Clock::now_rfc3339` is the one thing the bus reads; `FixedClock` is the test implementation. There is deliberately no `SystemClock` and no RFC3339 formatter here: the repository's one formatter is `crates/council/src/clock.rs`, the bus may not depend on `crates/council`, and a second copy of the civil-date algorithm would be a second source of truth for time formatting in exchange for nothing this crate needs - the bus never parses a timestamp, because SQLite does the calendar arithmetic. The consequence is stated in the module and here: **the production clock is supplied by whoever wires the bus into the shell**, and it must produce the same fixed-width UTC shape, because the due check is a string comparison. (8) **`next_attempt_at` is normalized at enqueue.** It is written through SQLite's own `datetime`/`strftime`, so an offset in the sender's `created_at` becomes the equivalent UTC stamp. `messages.created_at` keeps the sender's spelling, because that column is the record of what the sender said rather than a value the bus compares. (9) **The transport failure vocabulary is the registry's.** `TransportError::{Unavailable, Timeout, ProtocolError}` map to `ADAPTER_UNAVAILABLE`, `TIMEOUT` and `ADAPTER_PROTOCOL_ERROR` - three codes that were registered and unproduced. No new registry code was needed, and `TRANSPORT_FAILURE` is deliberately not among them. (10) **The policy has an owner and a check.** `schemas/mcf-v2/bus-policies.json` declares `dispatch.max_attempts`, `dispatch.batch_size`, `backoff.base_seconds`, `backoff.multiplier` and `backoff.cap_seconds`, each group with a `rule` stating its semantics; `crates/bus/src/policy.rs` ships the same numbers as `pub const` defaults; and the gate reads both and requires them to agree, so a change to one that is not made to the other fails rather than drifting. The gate also checks the declared termination path **against the machine**: `terminal.on_attempt_budget_exhausted` must be `QUEUED -> EXPIRED` *and* that edge must exist in `transition-types.json`, so a policy cannot describe a path the contract forbids. (11) **Three indexes.** `outbox(dispatch_state, next_attempt_at)` serves the dispatcher's one query as both filter and order, `message_attempts(message_id, attempt_no)` serves reading a message's attempts back, and `dead_letters(project_id, created_at)` serves the dead-letter listing. All are additive and reach an existing database for the reason DEC-058 already gives. |
| Reason | A durable queue that nothing drains is not a queue, and the two questions a dispatcher must answer - "how many times has this been tried?" and "what happens when trying is over?" - have to be answered from stored state and from the contract, not from a counter in memory or a number in a code comment. Putting the numbers in a declared policy file with a gate check keeps them configuration, which is what the brief requires and what the design already says; putting the decision in a pure function keeps the retry behaviour reviewable in one match arm. |
| Compatibility impact | `Bus` gains `with_policy`, `dispatch_due`, `dispatch_policy` and `backoff_policy`, and its two private policy fields. `BusError` gains `Expired`, whose code is `DEAD_LETTERED`. `Storage` gains `due_outbound`, `record_failed_attempt`, `record_dispatched` and `expire_message`, and `expire_message` takes a timestamp rather than a `DeliveryAttempt` because an expiry is not an attempt. `StorageError` is unchanged. `outbox.next_attempt_at` now holds a normalized UTC stamp rather than the sender's spelling; nothing read it before. `workspace.manifest.json:schema_sources` and `schemas/mcf-v2/manifest.json` each gain one entry. No machine, state, edge, transition, event, command, priority lane, Tauri operation or UI event changes. |
| Migration/reconciliation | None required. | Tests affected | `crates/bus/tests/dispatch.rs` is new: twelve tests over the pure decision (including a negative count and a count past the budget), the pure backoff (growth, the cap, determinism, a flat multiplier and a hostile policy), a successful handover advancing to `DISPATCHED` with what was sent being byte-for-byte what was stored, a refusal leaving the message `QUEUED` with the attempt recorded and no event appended, the backoff actually holding a message back, exhaustion terminating at `EXPIRED` with a dead letter carrying the last **real** failure, batch size bounding one pass, the first due time being normalized so an offset cannot misorder it, a persist failure stopping the pass, a dispatched message never being sent twice, the transport vocabulary being the registry's, and the shipped defaults matching the policy file. `crates/bus/tests/common/mod.rs` is new and holds the fixtures both bus test binaries share, so the envelope builder has one definition. `crates/bus/tests/enqueue.rs` now uses it. `tools/contracts/mutations.mjs` gains three proofs (`dec058-a`, `dec058-b`, `dec058-c`). |
| Known limitations | (1) **A pass is a read, not a claim.** Two dispatchers running at once both see the same due entries and both send them. That is safe for delivery - duplicate delivery is what the durable inbox exists to absorb, and the design says a crash "may cause duplicate delivery and must be safe" - but a second dispatcher's attempt row can collide with the first's, and the primary key on `message_attempts.attempt_id` refuses it rather than merging it. A claim would need a lease column this schema does not have. (2) **The bus ships no production clock**, as (7) states. Until something supplies one, only tests can dispatch. (3) **`message_receipts` and `inbox` are still untouched**, so nothing yet records that a recipient acknowledged anything; the machine's `RECEIVED`, `ACKED`, `PROCESSING`, `PROCESSED`, `REJECTED`, `DEAD_LETTER` and `RETRYING` states remain unreachable, as does the declared `RETRYING -> QUEUED` requeue. (4) **Backoff has no jitter**, deliberately, because the design requires determinism and this is a local single-user machine; a future multi-writer bus would want to revisit that, and the policy file is where it would be changed. (5) **`due_outbound`'s ordering is by `next_attempt_at` then `rowid`**, so entries that became due at the same instant are worked in insertion order rather than in priority order; priority lanes are a later slice and the control-lane requirement ("emergency control and recovery traffic must not be blocked by bulk model output") is therefore not yet met. |
| Related decision | Implements the retry, dead-letter and transport-boundary sections of `docs/MCF-V2-IMPLEMENTATION-DESIGN.md`, and the dispatch half of the `message_delivery` machine's declared edges. Applies AGENTS.md §5 (the contract wins on names and on state vocabulary - hence the gate check against `transition-types.json`), §7 (ACK is receipt, not success, which is why a successful handover is `DISPATCHED` and not `PROCESSED`), §9, §10 (structured errors, explicit transitions, no speculative abstraction), §12 and §16 (duplicate events, stale context, failure paths). Depends on DEC-034, DEC-055 and the enqueue half of DEC-058. Does not change DEC-029, and does not implement the durable inbox, receipt handling, gap detection, priority lanes, backpressure or replay. |

### DEC-058 the inbound side: the durable inbox, the receipt, and the processing spine

| Field | Value |
| --- | --- |
| Decision | The bus takes delivery of a message by validating its envelope, persisting its identity in the durable inbox, and only then acknowledging receipt; a redelivery is answered from that inbox and writes nothing; processing runs `ACKED -> PROCESSING` and ends at `PROCESSED`, `RETRYING` or `REJECTED -> DEAD_LETTER`, with retryability carried by which transition was taken and the reason carried by the event log. The `inbox.processing_state` and `message_receipts.receipt_state` vocabularies, left open by the enqueue and dispatch records, are now declared. |
| Classification | **ADDITIVE**: four `Bus` operations, seven `Storage` operations, five new public types, one `JcsValue::Bool` literal, one `BusError` variant and two declared vocabularies. No machine, state, edge, transition, event, command, table, column, index or registry code changes. |
| Previous behavior | The bus could persist, queue and dispatch a message and had no way to receive one. `inbox` and `message_receipts` were empty by construction; `ACKED`, `PROCESSING`, `PROCESSED`, `REJECTED`, `RETRYING` and `DEAD_LETTER` were unreachable; `message_receipts.receipt_state` and `inbox.processing_state` were undeclared, so any value written into them would have been invented on the spot; and `dead_letters` could only be reached by a sender whose transport budget ran out. Two consequences were latent. (1) **`acknowledged_at` had no writer and `terminal_event_id` had no writer**, so the two columns that make the inbox more than a set of ids were unexercised. (2) **The registry's `PROCESS_FAILED`** was registered and unproduced, with no path that could produce it. |
| New behavior | (1) **Persistence precedes acknowledgement.** `Bus::receive` validates the envelope with the protocol crate's validator, requires the project to exist and the identity to be new, and then writes, in one transaction, the message row, the inbox row in `PERSISTED`, the `DISPATCHED -> RECEIVED` transition and *then* the `RECEIVED -> ACKED` transition with its receipt. A crash between the two leaves a message that has been seen and not yet acknowledged, which a redelivery resolves; the reverse order would leave an acknowledgement of a message nothing recorded. (2) **A redelivery is not an error.** It returns `duplicate: true`, the state the message actually reached and its terminal event, and writes nothing at all — no second event, row or receipt. Recognising it from the existence of the inbox row rather than from a `DUPLICATE` state is what lets the state keep describing where the message got to. (3) **An arriving message is born `DISPATCHED`.** That is not a transition this repository performs: the message arrived, which means its sender dispatched it, and the receiver's part of the machine begins where the sender's ended. Both directions advance one `messages.delivery_state` column, so the machine describes one message's delivery rather than two half-machines. (4) **Two identity collisions are refused, not absorbed.** A `message_id` a known message holds is `DuplicateMessage` (code `DUPLICATE_CONFLICT`), because absorbing it would silently replace the first message's record under the first message's id; and a `(session_id, channel, sequence)` position already taken is `SequenceConflict` (also `DUPLICATE_CONFLICT`), because both directions share one ordering space per channel. (5) **Retryability is the transition.** A retryable refusal takes `PROCESSING -> RETRYING`; a terminal one takes `PROCESSING -> REJECTED -> DEAD_LETTER` through both edges rather than jumping to the end. There is no stored `retryable` flag, so a message cannot be marked retryable and simultaneously be terminal. (6) **The reason lives in the event log.** `message_receipts` has no column for a reason and the table is fixed, so the `ACTION_FAILED` payload carries the reason and the retryability, and the terminal path additionally writes it as the dead letter's `final_error_json` under the registry's `PROCESS_FAILED` — which gives that code its first producer. (7) **A refused transition names the state it found.** Every move goes through one guarded update whose `WHERE delivery_state = ?2` clause makes an illegal move a no-op, and the caller is told which state the row was in rather than that zero rows changed. That is what keeps the bus inside the machine even when its own bookkeeping is wrong. (8) **A receipt is one row per message, derived.** `receipt_id` is `rcpt_{message_id}`: `message_receipts` declares no uniqueness on `message_id`, so the derivation is what makes the relation one-to-one, and it is what lets an acknowledgement be updated to a non-acknowledgement without a second row appearing. `acknowledged_at` survives that update, so the two facts do not overwrite each other. (9) **A missing row is not a storage failure.** `StorageError::NotFound` now classifies as `SCHEMA_INVALID` rather than `STORAGE_FAILURE`: nothing is wrong with the database, and reporting it as a storage failure would send a caller looking for a broken disk. |
| Reason | A durable outbox with no durable inbox is a bus that can only talk. The two properties that make an inbound path safe — that nothing is acknowledged before it is recorded, and that a redelivery cannot become a second side effect — are exactly the two that cannot be established by reading the code that performs them, which is why the tests count rows instead of asserting `Ok`. |
| Compatibility impact | `Bus` gains `receive`, `start_processing`, `complete_processing` and `reject_processing`. `BusError` gains `DuplicateMessage` (code `DUPLICATE_CONFLICT`), and `StorageError::NotFound` now classifies as `SCHEMA_INVALID` instead of `STORAGE_FAILURE` — a code change for one condition, stated here because it is a behaviour change rather than an addition. `Storage` gains `receive_message`, `start_processing`, `complete_processing`, `reject_processing`, `inbox_row`, `receipt_row`, `message_exists`, `project_exists` and `message_at_position`, and the public types `IncomingMessage`, `InboxRow` and `ReceiptRow`. `canonical::JcsValue` gains `Bool`, completing RFC 8785's three literal forms. No schema, table, column, index, registry entry or contract file changes. |
| Migration/reconciliation | None. `inbox` and `message_receipts` were empty, so the newly declared vocabularies describe rows that did not previously exist. |
| Tests affected | `crates/bus/tests/inbox.rs` is new: fourteen tests over the receive path, duplicate delivery, the two identity collisions, the processing spine, both refusal paths and the refusal that names the state it found. `crates/bus/tests/common/mod.rs` is reused unchanged. |
| Known limitations | (1) **A message can only be received by the same database that dispatched it.** One SQLite file holds both directions, so `receive` finds the sender's outbox and attempts when it advances the shared `delivery_state`. That is what the local-first constraint means and it is why the end-to-end path is testable at all, but a message that arrives from outside this bus — an agent's reply — is born `DISPATCHED` with no outbox row, and the outbox-side bookkeeping for it is simply absent rather than wrong. (2) **`RETRYING` has no exit.** The machine declares `RETRYING -> QUEUED` (requeue) and `RETRYING -> EXPIRED`, and neither is implemented, so a retryably refused message currently waits forever. (3) **`inbox.terminal_event_id` is only set by the two terminal paths**; a message left `RETRYING` has none, which is correct but means the column does not identify "the last event". (4) **The contract gate does not read Rust for delivery states**, so an undeclared state written by the bus would be caught by these tests and not by the gate; adding that check is deferred, and it needs a mutation proof of its own before it can be trusted. (5) **`dead_letters.attempts` means the same thing on both paths** — delivery attempts — and a rejected message has exactly one, because a redelivery is answered as a duplicate rather than processed again; a message rejected after being requeued and redelivered would still report one, which is a defect that cannot yet occur because requeue is not implemented. |
| Related decision | Implements the inbound flow and the dead-letter section of `docs/MCF-V2-IMPLEMENTATION-DESIGN.md` and the receiver half of the `message_delivery` machine. Applies AGENTS.md §7 (ACK is receipt, not successful execution, which is why `ACKED` precedes `PROCESSING`), §12 (duplicate events and failure paths), §16 (duplicate events and failure paths are named validation targets), §19 and §22. Completes the vocabularies DEC-058 left open. Does not change DEC-029, and does not implement requeue, gap detection, priority lanes, backpressure or replay. |

### DEC-060 priority lanes

| Field | Value |
| --- | --- |
| Decision | A dispatch pass works the declared priority lanes in the contract's order before it considers how long each entry has been due. The lane ranking is a `CASE` over the stored envelope's `priority` in the due query, and the gate requires that ranking to equal `schemas/mcf-v2/registry.json`'s `priority_lanes`. |
| Classification | **REFINEMENT** of the dispatcher's ordering, plus one additive index. No machine, state, edge, transition, event, command, table, column, policy value or registry entry changes. |
| Previous behavior | The due query ordered by `next_attempt_at` then `rowid`. Lane order therefore had no effect at all: a bulk message that came due a second earlier than an emergency-control one was served first, and `docs/MCF-V2-IMPLEMENTATION-DESIGN.md`'s requirement that "emergency control and recovery traffic must not be blocked by bulk model output" was unmet. The priority was already in every envelope and already validated by the envelope contract; nothing read it. |
| New behavior | (1) **Lane first, then due time, then insertion.** Among the entries a pass is allowed to take, the lane decides; `next_attempt_at` breaks ties within a lane and `rowid` breaks ties within an instant. Lane-first is the ordering that satisfies the requirement: ordering by due time first would let a bulk message that came due marginally earlier consume the batch. (2) **The rank is derived from the stored envelope**, not from a new column: `json_extract(envelope_json, '$.priority')` reads the priority the contract already requires, so no schema change is needed and there is no second copy of the priority to disagree with the envelope. An unrecognised value ranks last rather than first, so a value the contract does not declare cannot jump the queue. (3) **`idx_messages_priority`** serves the expression. It is additive and reaches an existing database for the reason DEC-058 gives. (4) **The order is checked against the contract.** The lane names are read out of the SQL in order and required to equal `registry.priority_lanes`, because a `CASE` in a query string is exactly the kind of thing a type system cannot see and a reviewer can read past. |
| Reason | The lane order is contract data, and the requirement it serves is a product constraint rather than a preference. Putting it in SQL is the only place it can go without a column, which means the only thing standing between the requirement and a silent regression is a check that reads the SQL. |
| Compatibility impact | Dispatch order changes for any backlog containing more than one lane. `Storage::due_outbound`'s contract is otherwise unchanged. One new index. No new error code, no new policy value. |
| Migration/reconciliation | None. The index is created by the schema batch on open. |
| Tests affected | `crates/bus/tests/dispatch.rs` gains `a_pass_serves_the_control_lane_before_the_bulk_lane`: four messages due at the same instant in four lanes, a batch of three, and an assertion on the order they were handed over. `crates/bus/tests/common/mod.rs` gains `envelope_with_priority`, which `envelope_at` now delegates to. `tools/contracts/mutations.mjs` gains `dec060-a`. |
| Known limitations | (1) **Backpressure is still absent.** A pass is bounded by `batch_size`, which bounds one pass and not the queue, so a producer can still grow the backlog without limit. (2) **Gap detection is still absent**, so a message arriving out of order is accepted with nothing recording that something was missed. (3) **`RETRYING` still has no exit**, so a retryably refused message waits forever; `RETRYING -> QUEUED` is the next item. (4) The lane ranking is evaluated per candidate row, so a very large backlog pays for the `json_extract` on every candidate the query examines rather than only on the rows it returns. |
| Related decision | Implements the control-priority and ordering sections of `docs/MCF-V2-IMPLEMENTATION-DESIGN.md`. Applies AGENTS.md §5 (the contract wins on lane order, hence the gate check), §10 (no speculative abstraction: the priority is read from the envelope rather than duplicated into a column) and §16. Depends on DEC-058. Does not change DEC-029. |

### DEC-061 event identity for a transition the machine performs twice

| Field | Value |
| --- | --- |
| Decision | A transition event's id is derived from the message, the event type **and the pass**, where the pass is the count of events already recorded for that message and event type, read inside the transaction that appends the next one. The first occurrence keeps the plain id. |
| Classification | **REFINEMENT** of event identity. No machine, state, edge, transition, event type, command, table, column, index, registry entry or policy value changes. |
| Previous behavior | `transition_event_id` derived `evt_{message_id}_{event_type}`, which is deterministic and therefore collides as soon as one message legitimately produces the same event type twice. It cannot, as long as every message takes each edge at most once - and that is exactly what the unimplemented `RETRYING -> QUEUED` edge breaks, because a requeued message runs `QUEUED -> DISPATCHED -> RECEIVED -> ACKED -> PROCESSING` again. The defect surfaced as `UNIQUE constraint failed: events.event_id` while implementing requeue, and it would have blocked replay for the same reason: replay re-runs a transition. Two earlier attempts to work around it - `INSERT OR IGNORE` on `messages` and on `inbox`/`message_receipts` - were correct for those tables and wrong for `events`, because silently ignoring a second transition makes the event log omit a transition the machine performed. AGENTS.md §12 requires immutable history preserved, so the log has to record both. |
| New behavior | (1) **The pass is durable state, not a counter in memory.** `next_transition_event_id` counts the events already recorded for that message and event type inside the appending transaction, so a crash and retry derives the same id rather than a new one. That is the property the plain derivation exists to provide, and a random or timestamped id would lose it. (2) **The first occurrence is unchanged.** `evt_msg_1_message_queued` stays `evt_msg_1_message_queued`; only a repeat is suffixed. No event already written is renamed, and no existing database's log becomes inconsistent with the ids its own rows carry. (3) **The prefix test is `instr`, not `LIKE`.** The base id contains underscores, which `LIKE` treats as single-character wildcards, so a `LIKE` pattern would have over-matched and counted unrelated events - producing a wrong pass number under a hash chain, which is precisely the silent corruption this work exists to prevent. (4) **`transition_event` returns `Result`**, because deriving the id is now a read that can fail; all eight call sites propagate it. (5) **The pass number is not a sequence.** The event's `sequence` remains its chain position, derived from the chain tail; the pass is part of the id and nothing else. |
| Reason | The event log's job is to record what the machine did. A derivation that can only express "once" forces the log either to lose a transition or to refuse the transition, and both are worse than an id that says which pass it belongs to. |
| Compatibility impact | `transition_event` is private to `crates/storage` and now returns `Result`; `transition_event_id` keeps its meaning for first occurrences. Event ids for a message that takes an edge twice gain a `_{n}` suffix. Nothing else changes. |
| Migration/reconciliation | None. Every id already written remains valid and remains what the log says it is. |
| Tests affected | `crates/bus/tests/inbox.rs` gains `a_retryably_refused_message_can_be_requeued_and_processed_again` (a full round trip: refused, requeued, re-dispatched, re-received, re-processed, with all ten events in order and still one inbox row and one receipt) and `a_repeated_transition_gets_its_own_event_id_and_the_first_keeps_the_plain_one`. `a_retryably_refused_message_can_be_requeued_and_processed_again` is the test that found the defect. |
| Known limitations | (1) **The pass count is a count, not a monotonic counter**, so it is correct only while events are never deleted; the log is append-only, so it is, but a future pruning feature would have to revisit this. (2) **`RETRYING -> EXPIRED` is still unimplemented**, so a message refused retryably and never requeued waits in `RETRYING` rather than expiring - the caller's decision is now the only way out, which is deliberate but leaves a message that no caller revisits stuck. (3) The suffix is part of the id and therefore part of what DEC-034 hashes, so an id and its hash move together and neither can be changed alone. |
| Related decision | Unblocks the `RETRYING -> QUEUED` edge DEC-059 left without an exit, and is a prerequisite for the replay slice. Applies AGENTS.md §12 (preserve immutable history) and §19 (do not normalize a disagreement away). Depends on DEC-034 and DEC-058. |

### DEC-062 the last declared exit: RETRYING to EXPIRED

| Field | Value |
| --- | --- |
| Decision | A message that was refused retryably and never requeued can be terminated at `EXPIRED` through the declared `RETRYING -> EXPIRED` edge, with a `dead_letters` row, its queue entry abandoned if it has one, and `inbox.processing_state` set to `EXPIRED` with the terminal event recorded. |
| Classification | **ADDITIVE** at the crate's surface (one `Bus` operation, one `Storage` operation) and at one declared vocabulary; no machine, state, edge, transition, event type, command, table, column, index, registry entry or policy value changes. |
| Previous behavior | `RETRYING` had no exit. DEC-059 gave it one by requeueing, and DEC-061 made requeue work, but requeue is a decision the caller takes - so a caller who never took it left a message in `RETRYING` **forever**, with nothing recording that it was stuck. That is worse than a failure, because a failure is visible. It was the only state in the machine whose declared exits the bus did not implement. |
| New behavior | (1) **The edge, not a new state.** The message ends at `EXPIRED`, which is the state the transition record declares, and `DEAD_LETTER` stays reserved for `PROCESSING -> REJECTED -> DEAD_LETTER` - a receiver refusing a message outright. A message that could not be processed in time was never refused, so calling it dead-lettered would have been the wrong word for the right outcome. (2) **`inbox.processing_state` gains `EXPIRED`.** The vocabulary DEC-059 declared was `PERSISTED`/`ACKED`/`PROCESSING`/`PROCESSED`/`RETRYING`/`DEAD_LETTER`; the terminal state the machine now reaches is a seventh value, and adding it is what keeps the inbox's vocabulary a description of the machine rather than a list that happens to cover today's paths. (3) **The queue entry is abandoned only if it exists.** A message that was received and never queued has no queue entry, and the expiry must not create one: an abandoned queue entry for a message that never queued is a row that records nothing. The `UPDATE` matching zero rows is therefore the correct outcome, not a silent failure - and the test asserts the absence rather than tolerating it. (4) **The reason recorded is the budget, not a refusal.** `dead_letters.final_error_json` is `PROCESS_FAILED` with "the processing budget was exhausted", because there is no stored processing-attempt count and so no particular refusal is the cause; the refusals themselves are already in the event log, which is where DEC-059 put them. (5) **The dead-letter insert is `ON CONFLICT DO NOTHING`**, so expiring a message that somehow already has a dead letter cannot fail on the primary key. |
| Reason | A state machine with a state no implementation can leave is a machine that describes behaviour the system does not have, and this repository's rule is that the contract leads - so either the exit gets implemented or the gap gets recorded. It was recorded in DEC-059 and DEC-061 as a known limitation; this closes it. |
| Compatibility impact | `Bus` gains `expire_retrying`; `Storage` gains `expire_retrying`. `inbox.processing_state` gains `EXPIRED`. `RETRYING -> EXPIRED` becomes reachable, so `MESSAGE_EXPIRED` now has two producers (`QUEUED -> EXPIRED` from a transport budget, `RETRYING -> EXPIRED` from a processing one). |
| Migration/reconciliation | None. The vocabulary addition describes rows that could not previously exist. |
| Tests affected | `crates/bus/tests/inbox.rs` gains `a_message_refused_retryably_and_never_requeued_can_be_expired` and `expiring_a_requeued_message_abandons_its_queue_entry`. The second also exercises a pass count above two: a message refused, requeued and refused again reaches `evt_msg_x_3_action_failed_2`, which DEC-061's limitation note recorded as untested. |
| Known limitations | (1) **There is no processing budget**, so this is a caller's decision rather than a policy: `bus-policies.json` declares a delivery attempt budget and nothing for processing, because the schema stores no processing-attempt count to spend. A policy for it would need a stored count that does not exist. (2) **`dead_letters.attempts` is `1`** on this path, meaning the one delivery that brought the message here; it does not count processing attempts, for the same reason. (3) **Every declared state now has an implemented exit, but not every path through the machine is exercised**: `PROCESSED` and `DEAD_LETTER` are terminal by declaration, and the remaining unreached combination is a message requeued more than once before expiring. |
| Related decision | Closes the limitation recorded in DEC-059 and DEC-061. Implements the dead-letter section of `docs/MCF-V2-IMPLEMENTATION-DESIGN.md`. Applies AGENTS.md §5 (the contract declares the edge, so the implementation provides it), §12 and §22. Depends on DEC-058, DEC-059 and DEC-061. |

### DEC-063 ordering gap detection

| Field | Value |
| --- | --- |
| Decision | An arrival that skips an ordering position is accepted and reports the gap. The gap is derived from the highest durable position in the `(session_id, channel)` stream, returned on the receive outcome, and stored nowhere. |
| Classification | **ADDITIVE**: one `Storage` read, two new public types, one new field on `Received`. No machine, state, edge, transition, event type, command, table, column, index, registry entry or policy value changes. |
| Previous behavior | The bus accepted every arrival whose exact position was free and said nothing about what was missing. The ordering space is one per channel shared by both directions, so a gap meant a message the peer had sent had never arrived - and nothing anywhere recorded that, so the only way to notice was for a reader to query the positions themselves and compare. `registry.SEQUENCE_GAP` existed with no producer. |
| New behavior | (1) **Reported, not refused.** Refusing an out-of-order arrival would discard the very message that makes the gap visible, and would leave the receiver with nothing to resync *from*: the gap is evidence, and destroying evidence to signal its existence is backwards. The design's answer to a gap is to request a resync, which is a decision the caller takes - the same shape as requeue and expiry. (2) **Derived, not stored.** The positions are already durable in `messages`, so "a position is missing" is a fact about the record rather than a fact beside it. A `gaps` table would be a second copy of a derivable fact, free to disagree with the positions it was derived from, and this schema has no migration runner to add one anyway. (3) **A first message in a channel reports no gap.** A high position is not a gap on its own; without a preceding position there is nothing to be missing from. (4) **A redelivery reports no gap**, because nothing new arrived and so nothing new can be missing. (5) **`expected` is the position the stream should have continued at** (`highest + 1`) and `found` is the one that arrived, so the missing range is `expected .. found` and a caller can ask for exactly it. |
| Reason | The ordering requirement is not "refuse anything out of order" - that would break the ordinary case of a message arriving late after its successor. It is "notice, and be able to say what is missing", which needs the gap in the outcome and needs the message kept. |
| Compatibility impact | `Received` gains a `gap` field, so a caller that ignores it silently loses the detection. `Storage` gains `highest_sequence`. `BusError` is unchanged: a gap is not an error. `registry.SEQUENCE_GAP` remains unproduced, because producing it would mean refusing the arrival. |
| Migration/reconciliation | None. |
| Tests affected | `crates/bus/tests/inbox.rs` gains four tests: a skipped position reports the gap and is still `ACKED`; an arrival at the next position reports none; a first message in a channel reports none; a redelivery reports none. |
| Known limitations | (1) **The gap is not persisted**, so it is visible only to the caller that received the out-of-order message; a caller that ignores the outcome cannot recover it later without re-deriving it, and nothing notifies anyone. (2) **`SEQUENCE_GAP` has no producer** and will not get one while a gap is a report rather than a refusal; if the project later wants the code emitted, the decision is whether a gap should be refused, which contradicts (1) of the new behavior and would need its own record. (3) **Only forward gaps are detected.** A message that arrives *behind* the highest position is indistinguishable from a late delivery and is accepted silently, which is correct for delivery but means a duplicate position below the frontier is not reported as an ordering anomaly. (4) **Backpressure is still absent**, so the queue can still grow without limit; it is the last named part of this slice. |
| Related decision | Implements the ordering and gap sections of `docs/MCF-V2-IMPLEMENTATION-DESIGN.md`. Applies AGENTS.md §10 (no speculative abstraction: no table for a derivable fact) and §16. Depends on DEC-059. Does not change DEC-029. |

### DEC-064 backpressure as measurement, and the missing capacity code

| Field | Value |
| --- | --- |
| Decision | `DispatchReport` reports `remaining`, the number of queue entries still awaiting handover when the pass ended, and `Bus::backlog()` reads the same fact without running a pass. The bus measures the backlog and the caller decides what to do about it. **The bus does not refuse an enqueue for capacity.** |
| Classification | **ADDITIVE**: one `Storage` read, one new field on `DispatchReport`, one new `Bus` read. No machine, state, edge, transition, event type, command, table, column, index, registry entry or policy value changes. |
| Previous behavior | `batch_size` bounded how many entries **one pass** claims, so a large backlog was worked through in bounded passes - but nothing bounded the **queue**, and nothing reported its size. A producer could add work indefinitely while each individual pass looked healthy, and the only way to see the backlog was to query `outbox` directly. |
| New behavior | (1) **`remaining` is read after the pass**, so it describes the queue as the pass left it rather than as it found it - and it counts entries whose message is still `QUEUED`, because a message that was handed over is `DISPATCHED` and one that terminated is `EXPIRED` or `DEAD_LETTER`, and neither is work still to do. (2) **`backlog()` exists separately from the report**, because a producer that has to run a dispatch pass to discover the backlog has already done the work it wanted to avoid. (3) **The measurement is a read of the queue**, not a counter beside it: a counter would be a second copy of a derivable fact, free to disagree with the queue it counts. (4) **No refusal, and no new error code.** |
| Reason | The three previous decisions in this slice - requeue (DEC-059/061), expiry (DEC-062) and gap detection (DEC-063) - all took the same shape: the bus reports a condition and the caller decides, because the bus has no standing to decide for the controller. Backpressure is the same case, and the registry settles it: there is no code that means "refused because too much work is outstanding". |
| Compatibility impact | `DispatchReport` gains a field, so a caller that ignores it loses the measurement. `Bus` gains `backlog`. `Storage` gains `pending_outbound_count`. `BusError` is unchanged. |
| Migration/reconciliation | None. |

#### DEC-064 open architecture gap: no error code for transient capacity

`schemas/error-v1/registry.json` holds 32 codes and **not one of them means "refused because too much work is
outstanding"**. The nearest are `TIMEOUT` (the work was attempted and did not finish), `PROCESS_FAILED` (the work
was attempted and failed), `STORAGE_FAILURE` (a write failed) and `SERVICE_POISONED` (the service is unusable).
None describes a refusal that is **transient and expected**: the same request would succeed later.

`POLICY_DENIED` was considered and rejected. Backpressure *would* be a policy - a configured bound on outstanding
work - so the code is superficially apt. But `POLICY_DENIED` means "you may not", which is permanent until the
policy changes, and capacity means "not right now", which resolves on its own. A caller cannot act correctly on a
code that conflates the two: one should stop asking, the other should wait and retry. Reusing it would be exactly
the silent normalization AGENTS.md §19 forbids.

**Recommendation (not yet approved).** Add a registry code for transient capacity, with `mcf_code: null`, following
the `TRANSPORT_FAILURE` precedent - which is already a registry code with no MCF counterpart because it names a
boundary condition rather than a protocol error. Capacity is the same kind of fact: the MCF protocol has no notion
of a sender being busy, because the bus is local and single-user, so no MCF error is right for it. This needs a
decision because it adds a code to the error contract, and the accepted constraint for this slice is that the
contract does not change.

Until it is decided, backpressure stays measurement-only. That is a real limitation, recorded above rather than
hidden behind a reused code.

### DEC-065 explicit controller-invoked replay

| Field | Value |
| --- | --- |
| Decision | `Bus::replay(message_id, ids, clock)` replays a **terminal** message as a **new** message. It rewrites the stored envelope with `json_set` - a new `message_id` from the injected `IdSource`, the next free `sequence` in the stream, a fresh `created_at`, and `causation_id` set to the original's terminal event - and enqueues it through the ordinary `enqueue`. `find_outbound_by_operation_in` now matches only **live** claims. |
| Classification | **ADDITIVE** (one `Bus` operation, one `Storage` read, one new trait with one test implementation, one new `StorageError` variant) plus a **REFINEMENT** of the DEC-058 idempotency rule. No machine, state, edge, transition, event type, command, table, column, index or policy value changes. |
| Previous behavior | A terminal message was the end of the line: `dead_letters` recorded it and nothing could bring it back. Replay was the last unimplemented part of this slice. |
| New behavior | (1) **Explicit, not automatic.** Nothing replays on its own. A dead letter is a record that a message failed, and deciding it deserves another attempt is a judgement the bus has no standing to make - the same reason requeue (DEC-059) and expiry (DEC-062) are decisions rather than timers. (2) **A new message, not a reset.** `messages.message_id` is a primary key and the original row still holds the terminal state that justified the replay, so reusing the identity would rewrite history rather than add to it. More decisively, the declared machine has **no `EXPIRED -> *` or `DEAD_LETTER -> *` edge**, so there is no transition to express a reset with even if one were wanted. The replay begins at `CREATED` like any other message. (3) **Exactly three envelope fields change, and the protocol already names them**: `crates/protocol/src/envelope.rs` records that "a retry legitimately carries a new `message_id`, a new `sequence` and a new `created_at`". A fourth, `causation_id`, is set to the original's terminal event so the log says why the new message exists rather than leaving it looking unrelated. (4) **`json_set`, not string surgery.** SQLite's JSON1 functions edit the stored document exactly; rewriting JSON by hand would be a parser written badly. (5) **The new `sequence` is the next free one**, because `(session_id, channel, sequence)` is unique and the original still holds its position - the replay takes a new one rather than stealing the old one. (6) **Idempotency now matches live claims only.** A replay carries the original's `operation_id`, because it *is* the same operation; without this narrowing the replay was refused as a duplicate of the very message it replays, and `Bus::replay` returned the original's identity. The rule's purpose is to stop one operation being queued twice **while it is still pending**, and once it has terminated, re-enqueueing it is precisely what a replay is. (7) **`IdSource` is injected**, like the clock, because a production source would have to read a clock or a random device and this crate performs no I/O; `FixedIdSource` is the only implementation shipped and is deliberately not a production one, since two runs of a real system must not mint the same identity. |
| Reason | The approved scope names replay as an explicit controller decision. Making it a new message is what keeps it inside the declared machine, and making it explicit is what keeps the bus from deciding on the controller's behalf that a failure deserves another try. |
| Compatibility impact | `Bus` gains `replay`; `Storage` gains `replay_source`; `StorageError` gains `NotTerminal`; `crates/bus` gains `IdSource`, `FixedIdSource` and the `id` module. `find_outbound_by_operation_in` changes, so an enqueue whose operation previously deduplicated onto a **terminal** message now creates a new message instead. |
| Migration/reconciliation | None. The idempotency narrowing changes future decisions, not stored rows. |
| Tests affected | `crates/bus/tests/replay.rs` is new, with six tests: a replay creates a new message that names its cause and leaves the original untouched; a replay can be dispatched by an ordinary pass under its own identity; replaying a message that has not finished failing is refused (`SCHEMA_INVALID`); replaying a message that does not exist is refused as `SCHEMA_INVALID` rather than `STORAGE_FAILURE`; a second replay while the first is live is **deduplicated** onto it, and a further replay after it terminates is a new message; a replay carries a fresh `created_at`. |
| Known limitations | (1) **Replay does not carry the dead letter forward.** The new message does not record which dead letter it answers beyond `causation_id`, and `dead_letters` has no marker for "replayed", so a reader must follow the event chain to see that a failure was retried. (2) **`dead_letters` has no `UNIQUE(message_id)`**, so nothing stops a second dead letter for one message; the replay does not create one, but the schema would allow it. (3) **A replay does not re-derive its `payload`.** The envelope is copied verbatim apart from four fields, so a replayed message carries the context of when it was first created - including `context_snapshot_id` and `state_digest` - which may be stale by the time it is replayed. Refreshing them would mean deciding what the current context is, which is the controller's knowledge, not the bus's. (4) **`FixedIdSource` is not a production source** and would collide across runs; supplying a real one is the shell's job, alongside the clock. (5) **A replay is not audited as a replay.** There is no `REPLAYED` event type in the contract and no state for it, so the only durable trace is the new message's `causation_id`. |
| Related decision | Completes the approved M2 scope. Implements the replay section of `docs/MCF-V2-IMPLEMENTATION-DESIGN.md`. Refines DEC-058's idempotency rule and depends on DEC-061 (a replayed message re-runs transitions, which needs pass-suffixed event ids), DEC-062 (the terminal state a replay comes from) and DEC-034. Applies AGENTS.md §5 (the contract declares no reset edge, so replay is a new message) and §10. |

### DEC-066 the gate reads the Rust for delivery edges

| Field | Value |
| --- | --- |
| Decision | `tools/contracts/verify.mjs` scans `crates/storage/src/lib.rs` and `crates/bus/src/lib.rs` for `advance_in(tx, …, "FROM", "TO"` call sites and requires every `FROM->TO` to be an edge the `message_delivery` machine in `schemas/mcf-v2/transition-types.json` declares. | Classification | **ADDITIVE** to the validation tooling. No machine, state, edge, transition, event type, command, table, column, index, registry entry, policy value or crate changes. |
| Previous behavior | The gate read `bus-policies.json` and checked that the policy's declared termination path is a real edge, and it checked that the shipped Rust policy constants agree with the file. | Compatibility impact | `npm run verify:contracts` gains a check. The mutation harness gains one mutation, so it is now 32. |
| Migration/reconciliation | None. |
| Tests affected | None: this is a contract gate, not a Rust test. Its proof is `dec066-a`. |
| Known limitations | (1) **It covers the edges routed through `advance_in`, which is nine of the machine's thirteen.** The other four (`CREATED -> PERSISTED`, `PERSISTED -> QUEUED`, `QUEUED -> DISPATCHED`, `QUEUED -> EXPIRED`) are written as inline SQL in `enqueue_message_in`, `record_dispatched_in` and `expire_message_in`, where the from-state is implied by the `WHERE` clause rather than named as a pair - so the scan cannot read them as edges. (2) **It checks edges, not the four state vocabularies.** A literal state name written where no edge is involved - the inbound message's born state `DISPATCHED`, for instance - is not checked. (3) **It reads only two files.** A delivery state written in another crate would not be seen, which is correct today because only these two write those columns, but the check does not enforce that. |

#### DEC-069 Ordering gaps are surfaced, not repaired

| Field | Value |
